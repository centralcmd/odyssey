# Test Environment & End-to-End Testing Specification

## 1. Objective

Establish a repeatable, layered testing strategy for Odyssey, anchored by a
**synthetic data generator** that feeds three things from a single source of truth:

- realistic **demo data** for manual exploration and screenshots,
- **fixtures** for automated tests, and
- a known, deterministic dataset for **end-to-end (E2E) tests**.

The end state is a test pyramid with a healthy base (unit/service), a consolidated
middle (API integration), and a new top tier (browser E2E against the full Docker
stack), all sharing one set of data generators.

## 2. Current-state assessment

> **Historical snapshot.** This section records the state *before* the work this spec proposes, and is
> kept as the premise for the sections that follow rather than maintained. Much of it is now out of
> date: the E2E tiers exist, the API-test fixtures were consolidated into `Infrastructure/`, and
> permission claims are reconciled by `RoleClaimSeeder` rather than seeded by migrations. For how
> things work today, see `CLAUDE.md`.

| Layer | Status |
|---|---|
| Unit / service tests (`Odyssey.Core.Tests`) | xUnit + Moq + AwesomeAssertions on EF **InMemory**; fresh DB per test via `TestContextFactory` (seeds 3 currencies). Healthy. |
| API integration tests (`Odyssey.Api.Tests`) | `WebApplicationFactory<Program>` + InMemory + a `TestAuthHandler` injecting permission claims. Good coverage, but `ApiFactory` / `TestAuthHandler` / `TestClaimsProvider` are **copy-pasted across ~10 files**. |
| E2E | **None.** The existing Playwright usage is an ad-hoc design-system screenshot harness, not a test suite. |
| Synthetic data | **None.** No Bogus/Faker. `MigrationService.SeedDataAsync()` exists but is **empty** — a ready-made seam. Reference data (roles/claims) is seeded via migrations. `.env` defines `USER_EMAIL` / `TEST_USER_EMAIL` but they are not consumed by app code. |

Key gaps: no realistic/volume data, no E2E layer, integration-test boilerplate
duplication, and everything currently runs on EF InMemory (which hides
relational-constraint, cascade, transaction, and migration bugs).

## 3. Synthetic data approach

### 3.1 Decision

Use a **runtime EF Core seeder powered by [Bogus](https://github.com/bchavez/Bogus)**,
invoked from the existing `SeedDataAsync()` hook, **gated behind a flag** and
**deterministic by a fixed seed**.

### 3.2 Options considered

| Option | Verdict |
|---|---|
| SQL script | ❌ Drifts from the schema; painful across three databases plus migrations; no type safety. |
| Manual entry | ❌ Not repeatable, not CI-able. |
| EF `HasData` model seeding | ✅ for **reference data** (currencies, roles) — already used. ❌ for volume/demo data (migration-coupled, clumsy at scale). |
| Runtime EF seeder + Bogus | ✅ Type-safe, exercises real entities (and optionally domain services so validation runs), realistic volume, reuses the existing seam. |

### 3.3 Reference data vs. demo data

- **Reference data** (currencies, roles, permission claims): remains seeded via
  migrations / `HasData`. Always present, including production. In particular:
  - The full **ISO 4217 currency set is already seeded** via `HasData` in
    `OdysseyContext` — the demo seeder **must not** create or re-seed `Currency` rows.
  - **Roles and permission claims are already seeded** (the four canonical roles in
    `RoleDefinitions` — Admin / Owner / User / Guest — and their `PermissionClaims`).
    The demo seeder **must not** invent new roles, permission claims, or
    role-claim mappings; it only **assigns existing roles** to the seeded users.
- **Demo data** (a known login user, accounts, budgets, transactions,
  contacts, tags, files): generated by the runtime seeder. Never present in
  production.

### 3.4 Dataset profile

The seeder produces a **clean demo dataset** — modest volume, optimized for
realistic-looking screenshots and predictable E2E assertions (not a high-volume
stress dataset). Quantities are chosen so charts, budgets, and lists look populated
without overwhelming the UI: on the order of a handful of accounts, a few budgets,
and a few months of transactions per account.

### 3.5 Seeder requirements

1. Lives in a dedicated `Odyssey.Seeder` project (or a `DataSeeder` class wired into
   `MigrationService`), filling `SeedDataAsync()`.
2. **Deterministic** — fixed `Randomizer.Seed` so every run produces identical data
   (required for stable E2E assertions and screenshots).
3. **Idempotent** — detect a sentinel (the demo user) and no-op if already seeded.
4. **Environment-gated** — runs only when the host environment is Development or Testing;
   `Seed:DemoData` can turn seeding *off* there but cannot turn it on anywhere else
   (issue #457, item B4). **Impossible to run outside those two environments.**
5. Seeds **fixed E2E login users**, one per role, so login and authorization are
   deterministically testable across the full permission matrix. All four share a
   single fixed, known password — `Odyssey!Demo1`.

   | Email | Role |
   |---|---|
   | `admin@demo.example.com` | Admin |
   | `owner@demo.example.com` | Owner |
   | `user@demo.example.com` | User |
   | `guest@demo.example.com` | Guest |

   Roles are the canonical ones from `RoleDefinitions` (Admin / Owner / User / Guest).
   Users are created pre-confirmed (see §3.5a). **Finance data is not user-scoped** —
   `Account` has no owner FK and services filter only by entity id — so **all users
   have access to all accounts** (and all transactions/budgets). The users differ only
   by **role/permission** (what actions each may perform), not by what data they see;
   the demo accounts are a single shared dataset (see §3.7).
6. **Realistic distributions** — transactions backdated over months, mixed
   currencies, some archived accounts, varied contacts and tags — so charts and
   budgets render meaningfully.
7. **Currencies are referenced, never created.** Demo accounts/budgets/transactions
   pick from the existing ISO 4217 currencies already seeded in `OdysseyContext` (the
   seeder looks them up by `CurrencyCode`). Use a small, realistic subset of common
   codes — e.g. `USD`, `EUR`, `SEK`, `GBP` — rather than the full list, so the demo
   stays clean.
8. **Exchange rates are seeded so accounts convert.** Unlike currencies, exchange
   rates are *not* reference data — without them, multi-currency accounts can't be
   converted to the display currency and the UI flags every one. The conversion
   service does **no inversion or triangulation** (a `(to,from)` rate does not satisfy
   a `(from,to)` request), so the seeder inserts a **direct rate for every directed
   pair** among the demo currencies — the account currencies (USD/EUR/SEK/GBP) **plus
   `NOK`**, which has no account but is the default display/main currency
   (`AccountController.DefaultMainCurrency`) that the totals/net-worth view converts
   into. (Miss it and *every* account is flagged unconvertible, since none is NOK.)
   Rates are derived from one USD-value table so the matrix is internally consistent,
   with a short monthly history. Result: the whole portfolio converts, so currency
   warnings are eliminated by default. (To deliberately demo the warning UI, drop one
   currency's rates — e.g. SEK — leaving just its account(s) flagged.)

### 3.5a Demo/test environment configuration

To keep login deterministic and friction-free for the seeded stack and E2E runs, the
demo/test environment overrides Identity options so neither gate blocks automated
login:

- **No email confirmation** — `RequireConfirmedAccount = false` (and
  `RequireConfirmedEmail = false`). Seeded users are still created with
  `EmailConfirmed = true` as a belt-and-braces measure.
- **No two-factor requirement** — 2FA is left disabled on seeded users and is not
  enforced at login.

These overrides apply **only** to the demo/test configuration (the Development and Testing
environments); production retains its stricter defaults
(`RequireConfirmedAccount=true`).

### 3.5b Orchestration parity (Aspire & Docker Compose)

Seeding behaves **identically** under both local orchestrators because both run the
same `Odyssey.MigrationService` (where the seeder lives) and both back MariaDB with a
**named persistent volume**. In both: first boot on an empty volume runs the full
deterministic seed; every later boot/rebuild sees the sentinel and skips; data
persists. The differences are operational only:

| Concern | Docker Compose | Aspire |
|---|---|---|
| Gate-flag source | `.env` / compose `environment:` | AppHost `appsettings` + user-secrets (`Aspire:*`) |
| Force a fresh reseed | `docker compose down -v` | `docker volume rm <DataVolumeName>` (Aspire stop does **not** remove volumes) |
| Env-var source | `.env` | AppHost config / user-secrets |

Operational notes:

- The seed gate (`Seed:DemoData` / the host environment name) must be set in **both**
  config mechanisms — wiring one and forgetting the other is the easy mistake. Note the
  migrations host reads `DOTNET_ENVIRONMENT`, not `ASPNETCORE_ENVIRONMENT`.
- Both stacks bind host port **3307**, so they cannot run simultaneously; Aspire also
  has a known fresh-volume readiness race that only matters right after a wipe-reseed.

### 3.6 Shared generators

Bogus generators live in a shared `Odyssey.TestData` helper consumed by the seeder,
unit tests, and E2E setup. There must be exactly **one** definition of "a realistic
account / transaction / budget."

### 3.7 Demo accounts

Accounts are the top-level unit, and the `AccountType` values behave differently
(assets vs. liabilities, interest-bearing vs. not, monetary vs. property/vehicle), so
the demo set is **fully enumerated below** rather than randomized. Because finance
data is not user-scoped (§3.5), this is **one shared portfolio** visible to all four
users; there is no per-user split. Design rules:

- **Coverage** — every real `AccountType` appears at least once. `Unknown (0)` is a
  sentinel and is deliberately never seeded.
- **Time window** — the reference "today" is the seed run date; this spec uses
  **2026-06-19** as the anchor. Accounts span from **~10 years back (2016)** to brand
  new. *Long-lived* accounts (≈10 years of history) are concentrated on **checking,
  savings, investing, and loan** types — these drive the most interesting charts and
  balances.
- **Closed accounts** — a few accounts are closed (`Closed` set) to exercise the
  closed/archived flows and historical reporting.
- **Multi-currency** — the shared portfolio mixes `USD`, `EUR`, `SEK`, and `GBP` so
  conversion and aggregation are exercised.
- **Account numbers** — synthetic but shown **in full** (this is fake data, nothing
  to hide): plain numeric account numbers for domestic banks, plausible IBANs for the
  European accounts, full card numbers for cards, and structured loan references (e.g.
  `ML-2017-88431`). They are not real and need no masking. Property / Vehicle / Cash
  accounts have no account number (`null`).

All dates are deterministic anchors reproduced exactly by the fixed seed.

### 3.9 Demo budgets (one per year)

A budget is seeded for **each calendar year the data spans — 2016 through 2026
(11 budgets)** — so year-over-year budget reporting is exercised. Each budget:

- `Name` = `Household Budget {year}` (e.g. `Household Budget 2019`).
- `StartDate` = `{year}-01-01`, `EndDate` = `{year}-12-31` (the 2026 budget runs the
  full year even though "today" is mid-year).
- `BaseCurrencyCode` = `USD`.

Each budget contains the **same canonical set of budget items**, each linked to a tag
(`TransactionTagId`) with a `CategoryType` and a `PlannedAmount`. The base-year (2016)
amounts are below; later years are derived deterministically:

> **Escalation rule:** for budget year *Y*, `PlannedAmount = base × growth^(Y−2016)`,
> rounded to the nearest 100. `growth = 1.04` for **Income** items and `1.03` for
> **Expense** items.

### 3.11 Demo transactions

Transactions are too numerous to enumerate, so they are **generated from a fixed set
of recurring "streams"** plus light deterministic jitter — reproducible because the
Bogus `Randomizer.Seed` is fixed. Correctness rules that the seeder must honour:

- **Sign convention** — balance is `Sum(Amount)` (see `AccountTotalsService`), so
  **income is positive, expense is negative**. Budget `PlannedAmount`s are positive;
  the matching actuals are negative sums for expense tags.
- **Budget currency match** — `BudgetReport` only counts transactions whose
  `CurrencyCode` equals the budget's `BaseCurrencyCode` (USD); others increment
  `ExcludedTransactionCount`. So **USD-account streams drive budget actuals**, while
  the EUR/SEK/GBP accounts deliberately exercise the *excluded-currency* path.
- **Tagging** — tags attach via `TransactionTagLink` join rows (the skip-nav
  `TransactionTags` is read-only); the seeder must insert the join rows or budget
  matching (`TransactionTagLinks.Any(...)`) misses them.
- **Lifetime bounds** — a stream only emits while its account is active
  (`Opened ≤ TimeStamp ≤ Closed ?? today`).

§3.9 rule so actuals track the year's budget):

\* High-frequency streams (Dining Out, Fuel, Rideshare, Clothing, Card spend) are only
densely generated for the **most recent 24 months**; before that they fall back to a
monthly summarized entry. Monthly/quarterly/yearly streams run across the **full
account lifetime**. This keeps the dataset clean (recent activity looks rich, deep
history stays light) while every yearly budget still has matching actuals.

**Per-transaction attributes:**
- **Amount jitter** — each instance varies ±10% around its base (deterministic), so
  actuals approximate but don't exactly equal the budget.
- **Currency** — equals the account's `CurrencyCode`.
- **Status** (`TransactionStatus`) — ~80% `Approved`, ~15% `New`, ~5% `Flagged`;
  flagged ones get a short `StatusComment`. `StatusChangedAt` is set realistically.
- **Description** — human-readable per stream (e.g. "Weekly groceries — Whole Foods").
- **Paired transfers** — savings/investment/card-payment streams create two linked
  entries (an outflow on the source account and an inflow on the destination) so
  cross-account net worth stays coherent.
- **Files** — a handful of transactions (and accounts) get an attached demo file
  (receipt/statement) to exercise the file-association flows; see the file section if
  added later.
- **Opening / principal entries** — because every balance is just `Sum(Amount)`, each
  account starts with a dated opening entry on its `Opened` date: an opening deposit
  (+) for asset accounts (e.g. a starting brokerage/savings balance) and a principal
  disbursement (−) for loans/mortgages (the debt taken on), which subsequent payment
  streams then pay down toward zero. Closed accounts are driven to ≈0 by their
  `Closed` date.

## 4. Test pyramid

### 4.1 Tier 1 — Unit / service (exists)

Keep as-is. Refactor inline data construction to use the shared `Odyssey.TestData`
generators where it reduces duplication.

### 4.2 Tier 2 — API integration (exists; consolidate + add a real-DB slice)

- Extract the duplicated `ApiFactory` / `TestAuthHandler` / `TestClaimsProvider` into
  one shared fixture under `Odyssey.Api.Tests/Infrastructure/`.
- Add a focused **Testcontainers-MariaDB** variant for a subset of tests, to catch
  what InMemory silently passes: relational constraints, cascade deletes,
  transactions, and the actual migrations.

### 4.3 Tier 3 — E2E (new)

- **Playwright for .NET** driving the full `docker-compose` stack
  (NGINX → Blazor WASM → API → MariaDB), against the synthetic dataset and the fixed
  demo user. Browser tests live inside the .NET solution and reuse the DTOs and
  shared generators.
- Owns its **database lifecycle**: reset to a known state before each run
  (`docker compose down -v && up`, or a `Testing`-only `/test/reset` endpoint).
- Initial smoke flow: login → dashboard → create account → add transaction → budget
  reflects it → file upload.

## 5. Best practices (cross-cutting)

- Deterministic seed → reproducible data and stable assertions/screenshots.
- Idempotent and flag-gated seeding; demo data physically cannot reach production.
- A single source of generators shared by seeder, unit tests, and E2E.
- E2E owns its DB lifecycle; never assert against mutable shared state.

## 6. Decisions

1. **E2E tooling** — **Playwright for .NET.** Browser tests live in the .NET solution
   and CI, reusing the DTOs and shared generators.
2. **Dataset profile** — **Clean demo.** Modest, realistic volume optimized for
   screenshots and predictable assertions; not a high-volume stress dataset. See §3.4.

## 7. Rollout order

1. `Odyssey.TestData` shared Bogus generators; reference-vs-demo split.
2. Fill `SeedDataAsync()` with the gated, idempotent demo seeder + fixed demo user.
3. Wire a `seed` flag into Docker Compose / Aspire for the dev and test stacks.
4. Consolidate the duplicated `ApiFactory` fixture.
5. Add the Testcontainers-MariaDB integration slice.
6. Stand up Playwright .NET with the first smoke flow.
