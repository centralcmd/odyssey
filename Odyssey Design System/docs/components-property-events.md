# Components — Property events

> Part of the [Odyssey Design System](../README.md) docs. Foundations, tokens and the component catalog live in the README; this file is the per-feature detail.


The **Events** section (`PropertyEvents.jsx`, dialog `AddPropertyEventModal.jsx`, seed + helpers `property-events-data.js`; specimen `preview/explore-property-events.html`) is the **last** zone of the expanded property record. It is the contract events log applied to a house, cabin, car or boat: the same DS **`EventRail`**, the same *Recorded by … (automatically generated)* attribution line, the same **Today** cap on page one, the same rule that *New event* lives in the record's ⋯ menu and not on the section, the same three free-text fields (title on the rail, description under it, notes in the dialog only, with the audience stated), and the same full-replacement `PUT`. It reads `GET /api/properties/{id}/events` under `properties.read`; every write needs `properties.update`. Guest reads the log with no row actions.

**The type list is the property's type.** `PropertyEventType` has 21 members at ordinals **100–120** (disjoint from `ContractEventType`, which stays below 100 — the two share one table). **`PropertyEventTypeMatrix`** makes 17 legal per property type: 13 universal, plus *Renovation · Tax assessed · Tenancy started · Tenancy ended* for real estate or *Serviced · Tyre change · Periodic inspection · Registration* for vehicles. The DS **`PropertyEventTypeSelect`** takes `propertyType` and offers only those, type-specific first under *For vehicles* / *For real estate*, then *Any property*, with `Other` last. The `422` keyed `type` is therefore unreachable through the UI; the dialog still maps it inline.

**System-only members are never offered on create.** *Archived · Restored · Acquired date cleared · Disposal reversed* are written by the server alone. Editing a recorded row that carries one passes it as `keepType`, so the picker offers it alone under *Recorded automatically* and the `PUT` can keep it. Changing it to a user type is allowed; changing back is not.

**What the server records, and what it does not.** `PropertyService` stages a System row in the **same save** as three changes: the acquired date set (*Acquired*, at `min(date, now)`) or cleared, the disposed date set (*Disposed of*) or cleared (*Disposal reversed*), and archive / restore. A re-date of a non-null date writes nothing. Titles and descriptions come from a closed catalogue (*Property acquired* / *Acquired on 5 September 2018.*) that never names the property, its address, registration, VIN or make/model. **Estimates write nothing** (Non-Goal 1): the log is read under `properties.read`, and an automatic *estimate added* row would disclose what `properties.estimates.read` withholds. The dialog says a hand-written **Valued** event is a log line, not an estimate. The Edit property dialog's date helpers say *Setting or clearing it records an event*. The empty state names exactly the three automatic sources.

**No event changes the property.** A hand-written *Disposed of* does not set `DisposedDate` (Non-Goal 5), so the Type field's help carries *Recording an event does not change the property. To set its acquired or disposed date, edit the property.* The status chip reads only the property's own fields.

**No filters in v1.** The endpoint carries `search`, `types`, `from`/`to`, `source` and the sort keys; the section surfaces none of them. The log is newest first, 25 a page, as on contracts.

**The foot marker has no author.** Property carries `CreatedAt` but no `CreatedByUserId`, so the marker reads *Property added {date}* only. An *Acquired* event recorded at creation usually predates it and correctly sorts below it.

**Collapsed card and delete.** The counts strip gains an **Events** count, and the delete confirmation lists the events it removes (the `CASCADE`). The count needs `ExistingProperty.EventCount`, which the backend spec does not include yet — the same request as `FileCount`.

> **Stack reality check.** Mirrors *Property Events — Backend (Draft v2)*, issue #167: the `ContractEvents` table renamed `Events` and widened by TPH (`OwnerKind` discriminator, nullable `ContractId`, new `PropertyId` FK **CASCADE**, `CK_Events_ExactlyOneOwner`, `CK_Events_TypeMatchesOwner`), four routes under `/api/properties/{propertyId}/events` on `PropertyEventsController`, and `PropertyService.Create` / `Update` gaining a `userId` for attribution. **No contract-event wire change**, so `ContractEvents.jsx` is untouched. A contract event id on a property route, or the reverse, is a `404`. `ContractEventSource` may be renamed `EventSource` (CLR only); the kit's `'user'` / `'system'` source values do not change.
