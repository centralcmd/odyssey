# Components — User profile picture

> Part of the [Odyssey Design System](../README.md) docs. Foundations, tokens and the component catalog live in the README; this file is the per-feature detail.


A signed-in user can attach, replace and remove **one** picture of themselves from their own `/account` page. It then stands in for their initials monogram wherever the application already identifies them: the `/account` profile card, the `/account` page header, the admin `/users` list row and the user **detail panel**. Specimens: `components/profile-picture.html` (the four surfaces + every state) and `components/image-crop-dialog.html` (the shared cropper). Reference builds: `ui_kits/web/ProfilePicture.jsx`, `ui_kits/web/Account.jsx`, `ui_kits/web/Users.jsx`.

**It reuses the contact image's *pipeline*, not its storage.** Same narrow allow-list (PNG / JPEG / still WebP — no GIF, no SVG), magic-byte check, 1024 px cap, animation rejection, metadata strip and re-validation; same shared crop dialog. But the bytes live in their own pair of identity tables with **zero** relationship to the domain file store, so a holder of `files.read` cannot read a colleague's face and an admin file export can never contain one. Storage is duplicated; the **validation pipeline is not** — one cropper, one container walk, one strip.

**The `ImageVersion` token is the whole interaction model.** Two response-only `Guid?` fields — `ProfileDto.ProfileImageVersion` (your own) and `ExistingUser.ProfileImageVersion` (per admin row) — carry presence *and* the cache key.

- `null` → render the monogram and **issue no request**. A 50-row `/users` page makes zero speculative image requests; there is no probe and no mostly-404 request anywhere.
- Non-null → *renderable by this caller*, not merely "a row exists": the projection nulls the token wherever the read path would refuse — today, an **administratively disabled** subject. Without that, `/users` (the page that lists disabled accounts) would render an `<img>`, take a `404` by policy, and flicker to a monogram.
- A **transient lockout is not a disable.** Five mistyped passwords must not hide a picture: a deliberate removal never reverts and a lockout reverts in ~5 minutes, so hiding it would hand any signed-in caller a password-spray confirmation channel. Account status stays in the text chip it already lives in.
- A replace **re-keys** the URL (`?v={version}`), which is what makes the browser re-request at all: the response is `no-cache` with a strong `ETag`, so revalidation is the hot path and an unchanged `src` string would never be re-fetched.

**Rules that matter to a designer.**

- **The page owns the token, not the control.** On `/account` the control sits in the profile card and the mark sits in the page header — two different components. The write returns the new token to the *page*, which re-renders both; a section-local token satisfies the upload and leaves the header stale.
- **The mark can be the control.** On `/account` the profile card already shows the avatar, so it takes `ProfilePictureField`'s `overlay` variant rather than a second block: Change / Remove sit on the picture and appear on hover. **Hover is never the only affordance** — the buttons are always-rendered, focusable buttons (so `:focus-within` reveals them for keyboard and touch, each with its own `aria-label`) and a small camera badge stays visible so the control is discoverable without hovering. The labelled `row` variant remains the default anywhere the avatar is not already on screen.
- **No administrator write path.** An admin can neither upload nor remove someone else's picture: the write endpoints take no user id at all, in route or body, so there is nothing to tamper with. The remedies for an abusive upload are **disable** (which also stops the read) or **delete** (which cascades the bytes away) — never editing another person's identity. One operational consequence for release notes: disabling puts the image beyond every endpoint, the administrator's included, so evidence has to be captured before disabling.
- **Read is gated by a new low-tier claim, `profile-images.read`, granted to every role including Guest.** It narrows nobody today; what it buys is a revocation lever that exists *before* release (claims are baked into the auth cookie at sign-in, so retrofitting one later de-authorizes live sessions). Revoking it from Guest is the supported way to narrow who sees colleagues' pictures.
- **The pre-claim window is an honest disabled state.** A session that predates the deploy does not hold the claim, so the client checks the claim *before* rendering `src` — and on `/account`, where the image **is** the feature, the control is **disabled** rather than accepting a write it cannot show: "Sign out and back in to manage your profile picture." The same disable covers **Remove**, a self-service erasure control, so the message has to say how to clear it. Folding the claim into the projection is not the fix — a `null` token would flip the button back to "Add picture" after a successful upload, which is worse than an honest dead end. On `/users` the image is decorative and the monogram is simply fine.
- **Sizing is `lg` (56 px)** — the same step the page header uses. "Large" means that step and nothing bigger; `Avatar` writes its size inline, so no page can enlarge it without a new size step on the atom.
- **Alt text follows what the image *is*.** `/account`: the subject of its own controls, so a descriptive alt. `/users` **list row**: decorative (`alt=""`) — the adjacent cell names the person. **Detail panel**: *not* decorative, because the neighbouring cell is a mono user id — it carries the subject's resolved display name. The panel had no mark before, so this is a new surface rather than a replacement.
- **A load failure is silent, and per row.** `Avatar.onError` swaps to the monogram; no broken-image glyph, no toast, nothing announced. The failed flag belongs to the consumer and must be **per row**, reset when that row's token changes — one page-level flag would blank every avatar in the table after a single failure.
- **Removing is confirmed; replacing is not.** A replace destroys the old bytes and there is no picture history, so the confirmation says the image is deleted rather than hidden. A completed removal is announced through the page's live announcer — `/account` has no general-purpose status region to borrow.
- **Nothing new is invented for the UI.** No new interactive widget: the cropper is the shared `ImageCropDialog`, the mark is `Avatar`, the control is `ProfilePictureField`, and every added control is a plain labelled button inside an already-audited card.
- **Caps are named constants, tightened at runtime.** `UserProfileImageLimits` mirrors `ContactAvatarLimits` (stored 2 MB / 1024 px, source 20 MB / 8192 px, output 512 × 512, JPEG q 0.85) and the effective cap is `min(instance upload cap, 2 MB)` — `min` only: a surface may tighten an instance-wide cap, never widen one an administrator has lowered. No number appears as a literal at a call site.
- **No picture in the navigation chrome**, none on attribution rows ("created by", "uploaded by"), no "pick an existing file", no Gravatar, no animated formats. The picture never becomes the sole carrier of any fact — role, status and email confirmation all stay in their text chips.

**Endpoints it stands in for.** `GET /api/profile-images/{userId}?v={version}` (gated on `profile-images.read`; `404` for an unknown user, no picture, **or** a disabled subject — byte-identical, so it is not a user-existence oracle) · `POST /api/profile/image` (self-scoped, no id, `200` with the new token — not `204`, because the client needs it to re-key the URL) · `DELETE /api/profile/image`. In Blazor, replacing `/account`'s `.ph-avatar` span and `/users`' `.avatar` monogram with `OdsAvatar` leaves their **scoped** `.razor.css` tint rules unreachable, so each surface's tone has to be carried across as `Bg`/`Fg` — the header's tint is a soft `color-mix`, not the avatar's solid primary fill.
