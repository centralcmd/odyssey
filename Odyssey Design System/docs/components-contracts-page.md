# Components — Contracts page

> Part of the [Odyssey Design System](../README.md) docs. Foundations, tokens and the component catalog live in the README; this file is the per-feature detail.


The **Contracts page** (`Contracts.jsx`) is the household-agreements screen at `/contracts` — one expandable record per contract, the sister of Accounts / Insurance / Tax Statements. Reference build: `ui_kits/web/Contracts.jsx` (seed + helpers in `ui_kits/web/contracts-data.js`, styles in `ui_kits/web/contracts.css`); page specimen: `templates/contracts`.

**It reuses the record scaffold; its net-new pieces are derived status, the one-of-three parties list, and the document references.** Header, expandable `.acct-item` rows, collapsibles, `InfoTile`s and the problem/signal system are all atoms documented for Accounts / Insurance. A contract is a **single active period** (start + optional end) — there is no renewal sub-history (v1 non-goal). Its **status** is *derived, never stored* — computed by the ordered rule in `contracts-data.js` (`conStatus`): **Archived → Draft/Ready** (unsigned) **→ Upcoming** (start in future) **→ Expired** (end in past) **→ Paused → Active**, against one request "today". The collapsed row's headline is the period anchor + a relative-days word (ends in N days / starts in N days / expired N days ago / open-ended). The feature accent is a warm **clay/bronze** (oklch hue 42) — distinct from brand tide, Insurance's indigo, and Tax's magenta; it evokes a signed agreement and never encodes money.

### Reference number

A contract carries one optional **`referenceNumber`**: the number printed on the paperwork (policy, agreement, customer or order number). It belongs to the **counterparty**, so it is **not unique**, and the UI has no "already in use" state or duplicate warning. No number on file is a normal state and draws nothing.

- **Dialog** (`AddContractModal`, create and edit). Uses **`ReferenceNumberField`**, directly under the name. The rules match the DTO: ≤ 64 characters, no Cc / Cf / Co / Cn character, trimmed, blank → `null`. Errors block Save, and neither the live errors nor the server's 400 repeat the value. On edit the field is pre-filled and sent back, because `PUT` is a full replacement. Emptying the field is the only way to clear it.
- **Detail**. A `Reference number` `InfoTile` after *Name*, holding a **`ReferenceNumber`**. It appears only when a value is stored. Copying is in the row ⋯ menu: **Copy reference number** sits just before *Copy ID* and appears only when a number is stored.
- **List row**. The meta line shows `ReferenceNumber size="sm"` after the type label. The part the search matched is marked, so a row found only by its number shows why it is listed.
- **Search and sort**. `?search=` also matches the reference number. The placeholder reads *Search name, reference, party…*. **Reference number** is the last option in *Sort by*. It sorts ascending by default and puts `null` rows last in both directions.
- **Carry-forward**. Every write that rebuilds the contract from a loaded record (Edit, Pause/Resume, Archive/Restore, Sign) must send `referenceNumber` back. In the kit, those writes spread the previous record. The shipped client has to name the field at each `new UpdateContract { … }` site.

### Money direction — Outgoing and Incoming

Every **contract term** carries a required **`TermDirection`** — **`Outgoing` (0)** or **`Incoming` (1)** — stated from the **household's** perspective, never from either named party's. Registry: `OdysseyData.termDirections` (glyph · hue · sentence), helpers `termDirection` / `termDirectionInfo` / `termDirectionApplies` / `termDirectionRefusal` / `termDirectionColor`, tag component `TermDirectionTag`. Specimen: `preview/31d-contract-term-direction.html`.

**`Outgoing` is the default, and that is what makes the change invisible where it should be.** Every term recorded before the field existed is a cost, so an omitted direction and a chosen `Outgoing` are the same fact, and every figure an existing file reports keeps its exact value. **Direction lives on the term, not the contract** — an employment agreement pays a salary *in* and deducts dues and a pension contribution *out*, so a single flag on the record could express neither. It is also a property of the **entry, not the series**: it is no part of `(owner, kind, labelKey)`, so correcting a mis-directed term is an ordinary replace that supersedes rather than forking the history. And the **magnitude stays positive** — income is never a negative amount; the direction carries the sign, and the only signed figure anywhere is the net.

**Direction is offered exactly where it means something: a term owned by a contract — every kind, fee and rate alike.** An arrears rate charges the tenant and a deposit rate pays them, which is the same fact a fee carries, so both are asked the same way in the same slot. No account surface reads a direction today, so an account term still refuses anything but `Outgoing`; its dialog states the asymmetry in one muted line (`AddTermModal`) so the missing field reads as a decision, not an omission.

**Reading it.** The control is a **segmented pair**, like the value-unit toggle: two values, both visible, no dropdown to open to learn the alternative, and a helper line stating the consequence of the current setting. On read surfaces the mark is the **word** (`.trm-dir`) in the current-term tile's foot line and beside the name in each history row — mint in, coral out, with the hue as redundant support and never the carrier. **There is no direction glyph, and that is a decision:** every arrow reads against *value* before it reads against the household (an up arrow says "gain", a down arrow "loss"), and the two unambiguous marks — a money bag, winged money — are emoji, barred from product chrome. Icons in this feature name the *period*, never the direction. **Every contract fee term states its direction, both ways.** An earlier revision stated `Outgoing` only on records carrying both sides; that made the caption's *absence* carry meaning a reader cannot see, and left two records with the same fee reading differently. The fact belongs to the term, not to the set of terms around it. On a **tile** the word sits as a muted mono sub-line under the title — the slot a contract party tile gives its from–to dates — and the **figure** carries the direction's hue (coral out, mint in). In a **history row** it is the same quiet caption under the name, with the in-force figure coloured and superseded rows left neutral. Rate kinds and account terms show nothing, because direction does not apply there. The Current terms divider counts the two sides (`4 values in force · 2 incoming, 2 outgoing`). An income-bearing collapsed row carries a **Money in** chip in its meta line; that marker is derived from the record's own in-force terms, and a production list needs either the detail payload or a list-level field the backend deferred.

**The header reports two sides and a net.** Four flat tiles — **Monthly out · Monthly in · Yearly out · Yearly in** — beside four breakdown tiles: the two record distributions, then **one money tile per period carrying the net per contract type** (signed and colored, closing with a ruled *Net* row for the whole file). That ruled row is where the net lives; net tiles of its own were tried and cut, because a subtraction restated beside its two operands earns nothing. The tile once named *Monthly run rate* is **renamed rather than reused**: the figure it holds is now one side of two, and a name that stayed would read as a total. **No gross ever mixes the sides**; the net is `in − out`, computed from the unrounded sums and rounded once, the only **signed** figure on the page (leading `+` when positive, mint; `−` and coral when negative), and it is null only when *both* sides are. One unconverted-currency list covers both directions — a currency with no rate to base is named and excluded from each gross *and* from the net, never folded in at 1:1 — so the net is partial exactly when the grosses are. The header signal gains a **Next receipts** group beside **Next charges**: same row shape, the **group heading names the direction**, the soonest-movement collapse is per **(contract, direction)**, and the cap applies **per list** so a file full of charges cannot starve the receipts.

### The signature lifecycle — Ready and Signed

A contract carries **two signature stamps** in the same shape as `Paused` and `Archived`: nullable UTC timestamps whose *presence* is the state and whose *value* is the moment. `Ready` means marked ready for signature; `Signed` means signed by all parties. A contract with no `Signed` stamp is **unsigned**, and reads **Ready** (its `Ready` stamp is set) or **Draft** (it is not).

**The signature layer sits above the whole date chain, and that is the point.** An unsigned contract with a future start date reads **Draft/Ready, not Upcoming** — its dates describe a term nobody has agreed to, and reporting Upcoming would assert a commitment that does not exist. An unsigned contract whose end date has passed reads **Draft/Ready, not Expired** — a term cannot lapse before it begins, and what the reader has to act on is an abandoned negotiation, not a retired agreement.

**Unsigned contracts are on file but not in force.** They are excluded from the **run rate**, the **by-type cost split** and the **upcoming charges** through the same single status gate that already excludes Paused, and the run-rate tiles name the exclusion in their foot line (`in USD · 1 paused, 2 unsigned excluded`) — a total that quietly dropped would otherwise read as a pricing error. They **are** counted in **by type**, which is a headcount of the agreements on file, not a cost split. A draft may carry a fully priced Fee term; the price is a quote, and it appears in the term history and nowhere else.

**Two write paths onto one PUT.** The row menu carries the one-click path in lifecycle order, one step at a time — **Mark ready for signature** → **Mark signed** → **Unsign** (a signed contract is never offered "Mark ready"). Marking ready is idempotent the way a pause is: a repeated mark keeps the original stamp, so "ready since" never resets. **Mark signed stamps `Ready` too when it is missing**, because a `Signed` without a `Ready` is refused server-side and a one-click action must not be able to compose an invalid write. **Unsign clears both**, and is never refused in any state — a guard on the way out is how a row gets stranded. The create + edit dialog carries the other path: **Ready for signature** and **Signed** as ordinary date fields below the term dates, so a paper contract signed last month is entered in one go. Neither is required; leaving both blank records a **Draft**, which is the normal case.

**Three guards, shared by create and edit** (`conSignatureError`), each naming its field: a signed date needs a ready date (`contract_signed_requires_ready`), cannot precede it (`contract_signed_before_ready`), and neither may be dated in the future (`contract_signature_date_in_future`). **Nothing constrains a stamp against the term dates** — signing after cover has begun is ordinary, and signing before a term starts is the normal case.

**Every write carries both stamps forward.** The dialog and the row actions all rebuild the whole record, so Archive, Pause and an unrelated field edit each pass `ready` and `signed` through explicitly. Omitting them clears them, flips a signed contract to Draft and drops it out of the run rate — the one regression this feature can cause, and it is caused by the write, not by the user.

**Reading it on the page.** The record body grows one tile per stored stamp, in lifecycle order ahead of Paused / Archived: **Ready for signature** (amber while unsigned, neutral once signed) and **Signed** (mint). A plain Draft adds no tile — the Status tile has already said so. The collapsed row stays at **full brightness** and is marked by a **dashed card edge**: nothing about it is settled yet, and it is the row most likely to need attention — the opposite reading to archived, which is dimmed because it is finished. **Pausing an unsigned contract is refused** with its reason in the menu ("Only a signed contract in force can be paused"), and **archiving one is allowed** — abandoning a negotiation is the likeliest reason to archive a draft, and a draft usually has no end date to wait for. The header's **Upcoming** panel gains an **Awaiting signature** group (Ready, unsigned) at warning severity; drafts stay out of it — a draft is work in progress, and the status filter is where you go looking for it.

**Parties are a one-of-three polymorphic link.** Each party row links exactly one of an **Account**, an **Institution** (a `Contact` — the user-facing label is "Institution", per the spec's §3 decision), or a **Property** (`ContractPartyKind.Property = 3`; ordinal 2, the retired Insurance policy kind, stays a permanent hole). A property party is drawn in its property type's hue with its **kind** (House, Car, Boat…) as the caption, from the minimal `ContractPropertyReference { propertyId, name, type }` — never an address, cadastral number, registration or VIN. Rows render the **minimal projection** only — kind icon + display name + a kind pill + the target's own type — never the fuller cross-claim record. `conResolveParty` resolves a party's scalar id to that projection.

**The party picker reuses the accessible `Combobox`; documents are uploaded.** The add-party dialog is a two-step flow: a **party-kind** card selector (Account / Contact / Property) then a type-to-filter `Combobox` whose options are **pre-loaded** for the chosen kind (no in-widget async fetch — the candidate lists are handed in up front, keeping it inside `Combobox`'s accessible contract). The inaccessible `CreateTransactionDialog` popover is deliberately not used. Parties are created from **scalar ids only** (no nested entities — the §6/§10 mass-assignment invariant), and already-linked targets are filtered out so a duplicate can't be submitted. **Documents are uploaded**, not picked from a library — the attach dialog reuses the shared `AfmUpload` dropzone (the same drag-drop/browse control as the Files page and account uploads) with the `ContractFileType` vocabulary, so every upload surface in Odyssey behaves identically; each uploaded file becomes a `ContractFile` tagged Signed / Amendment / Correspondence / Other, and each carries the four optional **document-validity** fields (valid from / to, issued, issued by) described in *Reference data — File types*. Documents are **editable after attaching**: the Documents table's row menu opens *Edit document* — type plus the four fields, no rename — and an archived contract drops that menu entirely.

**Every party carries a role, and the role list is fixed by the contract's type.** The add/edit party dialog reads `conRolesForType(contract.type)` and offers exactly the legal roles under two headings — *Suggested for <type>* then *Also allowed* — so the picker can never compose a write the server refuses; the `422` is a backstop, not a thing the user is walked into. There is **no default role**: the control opens on a placeholder naming the type ("Choose a role on this rental contract…"), the helper names what the type takes, and **Save is disabled until a role and a target are both chosen** — the client half of the server's `[Required]`. Editing a party that still holds a role the matrix now rejects (a pre-matrix row, or one stranded by a type change) keeps that role visible, says in a warning band that the server refuses it, and holds the save until it is re-roled. Uniqueness is `(contract, target, role)`, so the target picker withholds only the records already linked **in the selected role**.

**A type change that would orphan a party is refused before it is written.** Changing a contract's type in the edit dialog runs `conPartiesRejectedByType` against the *incoming* type; any rejected party turns the refusal on — the `422` **TypeChangeOrphansParties** — which names each offending party by **role, display name and `partyId`** exactly as the server's problem body does, states the two routes that work (**re-role them, or detach them**), and disables Save. Nothing is written client-side either, so the dialog and the server agree on what happened.

**A contract beneficiary blocks deletion of its contact.** A contact named as a `Beneficiary` on a contract refuses `DELETE /api/contacts/{id}` with the same `409` a policy beneficiary does, and clears through the same one-transaction detach valve — `ContactLinksBlockedModal` now carries both blocker classes. The payload is **claim-gated per class**: the **counts** are always shown, policy names need `insurance.read` and contract names need `contracts.read`, and a caller without the claim is told that is why the list is absent rather than shown an empty one. The detach demands `contracts.update` and `insurance.update` **only for the classes actually present**, and names the missing capability instead of silently offering the refused delete.

**Archive is a reversible action, distinct from delete.** The row's **action menu** carries **Archive / Restore** — archiving stamps `Archived`, restoring clears it; either way parties and documents are kept. **Archiving never locks the record** — terms, parties, documents and events all stay writable, because a contract that has ended is exactly when its final rent, last invoice or handover note gets recorded. Archived contracts are **hidden from the default list** and reachable only by adding *Archived* to the status filter; the hard **Delete** is a separate, irreversible menu row. Both meanings are always conveyed as text.

**The page summary** rides in the header **Overview**: a **run-rate** pair (monthly and yearly, in the workspace base currency) over the **Fee terms in force** on Active contracts — each amount projected by its cadence, `÷ IntervalCount`, converted via the shared FX helper, with any unconvertible currency named rather than zeroed; one-time and per-occurrence fees carry no rate and are excluded. Below it, four breakdowns: **by type**, **by status** (with an *Ending soon · Nd* row under Active — a slice of Active, not a fifth status), and the same run rate split **by type**, monthly and yearly. The header **signal** — labelled **Upcoming** — holds two groups: **Ending soon**, the Active contracts whose term ends within the *ending-soon* window (the `endingWindowDays` tweak), so a renewal cliff is never missed; and **Next charges**, each contract's soonest recurring charge inside the *charge* window (`chargeWindowDays`, 45 days), read forward from the **Fee terms in force** the way Subscriptions reads its billing interval forward into upcoming renewals — a periodic Amount term projected from its cadence anchor (`AnchorDate`, else `EffectiveFrom`), never past the contract's own end date. Nothing is scheduled or stored; the rows are a derivation. **Starting soon** lists the Upcoming contracts whose term begins inside the *ending-soon* window, and **Recently expired** lists non-archived contracts whose term ran out inside the same *ending-soon* window — the decisions still outstanding. The button takes the panel's worst severity — **error** when a term has expired, **warning** when one is ending soon, **info** otherwise, and its count is the two groups combined. Clicking any row jumps to the contract.

**A contract also carries its price.** The expanded record's sections run **Details → Parties → Current terms → Term history → Documents**, and the collapsed card's counts strip runs **Parties · Terms · Documents**. Those two term sections are documented in *Components — Contract terms*.

**A property party takes any role the type allows.** `ContractPartyKind.Property` and the role `Property` (18) are different enums: the kind says the target is a Property record, the role says what it does in the agreement. Nothing links them — the house on a mortgage is typically `Collateral`, on a lease `Property`, on a policy `Insured` — and the matrix is unchanged. **Archived and disposed properties stay linkable**; when one is picked the helper line says so, so history remains recordable. The write carries `propertyId` as a scalar only, and switching kind on edit is a full replacement recorded as *Party removed* + *Party added*. Specimens: `preview/58e` (edit dialog), `preview/60` (tiles, the property's Contracts section, delete).

> **Stack reality check.** Mirrors the *Contracts* backend (party role matrix, Draft v3): `Contract` + `ContractParty` (one-of-three: `accountId` · `contactId` · `propertyId`) + `ContractFile` (a `FileMetadata` reference), with `Status` derived on read against a single request clock. Read responses expose **minimal `{id,name,type}` projections** for each party target (not the full account/contact/policy record). Dialogs map to `NewContract` / the add-party + attach-file requests; archive is the `IsArchived` flag on the update DTO. The prototype computes status, the parties projection and the summary client-side in `contracts-data.js`.
