# Reference data — Contact aliases & lifecycle dates

> Part of the [Odyssey Design System](../README.md) docs. Foundations, tokens and the component catalog live in the README; this file is the per-feature detail.


A contact record carries a fourth child collection — **Aliases**, the alternative names a contact is actually known by — plus four optional lifecycle scalars. The point of the feature is that a search finds a contact under any name they go by, and that a dissolved insurer or a deceased counterparty on an old transaction *reads as historical* without being deleted or archived.

| Addition | Shape | Where it lives |
|---|---|---|
| **Alias** | `Value` (≤ 128, required, trimmed + whitespace-collapsed) + `Label` (≤ 64, optional **free text**) | On the **contact**, so Persons and Organizations use one mechanism. Own sub-resource endpoints, mirroring addresses / emails / phones. Cap **32 per contact** |
| **MiddleName** | `string?` ≤ 128 | `PersonDetails` |
| **DateOfDeath** | `DateOnly?`, not future, not before `DateOfBirth` | `PersonDetails` |
| **EstablishedDate** / **DissolvedDate** | `DateOnly?`, neither future, dissolved not before established; either may stand alone | `OrganizationDetails` |

**Rules that matter to a designer.**

- **The label is free text, not an enum** — "maiden name", "nickname", "trading as", "pre-merger name" — so a user names the naming relationship in their own words with no schema change. The consequence is accepted, not hidden: it is **not** searched, not filterable, not validated against a vocabulary, not localised, and two users may spell one concept differently. This deliberately deviates from the sibling collections, whose `Label` *is* an enum: those label a *channel* from a fixed set, this labels a *naming relationship* with none.
- **Aliases are names, not contact methods**, so they get their **own section above `Contact information`** under its own `SectionDivider` — emitted by the record card, which owns the headings (`ContactAliases` renders bare). The card's header count chips are the table of contents for the contact-information section and gain **no** alias glyph.
- **An alias is a tile, never a chip.** It needs a ⋯ menu at a ≥ 24×24 px target and a two-line body; `Chip` is a ~23 px nowrap pill that cannot host one. It is also **not** the contact-method tile grid — that model is positional, carries `IsPrimary`, an enum label and an assigned column. Hence a sibling grid with the same tile shell (`.odc-alias-*`).
- **Uniqueness is per contact, on the value alone**, case- **and accent**-insensitively: "Hansen" cannot be stored twice under two labels, and `Renee` clashes with `Renée`. Two *different* contacts may both be aliased "JR".
- **Rejections render inline, with no toast.** Duplicate (409), cap (422) and validation (400) keep the dialog open, set `aria-invalid` on the value field and move focus there. Only a 404 or transport failure closes the dialog and toasts. **Deleting is immediate** — no confirm dialog, matching the sibling tiles; an alias is cheap to re-add.
- **Menu gates are distinct.** The copy items (`Copy alias`, `Copy ID`) are unconditional, so the trigger is always rendered and the menu is never empty; `Edit` needs `contacts.update` **and** a non-archived contact; `Delete` needs `contacts.delete`. A principal holding update without delete must not be offered a Delete that 403s.
- **The cap is offered, not hidden.** With 32 aliases the action still appears and the save explains itself — client-side copies of a server cap are banned.
- **Search covers alias values and the middle name**, not the label. Hence the placeholder **"Search name, alias or notes…"**, and the `Updated` tile's caption **"bumped by any address, email, phone or alias change"** (every alias write bumps the parent's `UpdatedAt`, which keeps the vCard `REV` honest).
- **The middle name never enters the display name.** It is stored, shown as a tile and searchable, but stays out of the `First Last` fallback, so no contact's rendered name, search key or sort position shifts. In a vCard, `N` carries it while `FN` does not — accepted: `FN` is authoritative in vCard 4.0 and stays consistent with what Odyssey displays.
- **Recording a date changes no state.** Nothing is archived, nothing is unlinked; the contact stays selectable as a counterparty, custodian, insurance party and journal participant. Deceased / dissolved surfaces twice, both times as **text**: an outline `Chip` in the record card's `Chips` slot *after* the status chip (`Deceased 11 Mar 2024`), and a suffix folded into the picker **option's label** (`Kari Nordmann · Deceased`) — into the label, not a sub-line, so it lands in the accessible name by construction.
- **All three new dates are `DateField`s, and `DateOfBirth` migrates to one too.** The birth/death pair is validated from both sides, so each field needs its own `Error` channel — a bare `DatePicker` has none.
- **The tile grid is NOT `Dense`.** A Person card runs up to eleven tiles, past the grid's comfortable ceiling of eight, which is what argued for `Dense` — but dense hides the tile icon chip (`.odc-tilegrid.dense .odc-infotile-ic { display: none }`), and on a contact the icons are what make a long field set scannable. Contacts therefore take the extra grid row and keep their icons. Density is decided per record type, never mixed inside a card. A field with no value still renders no tile.
- **vCard.** One **grouped** `itemN.NICKNAME` per alias plus `itemN.X-ODYSSEY-ALIAS-LABEL` for the label — a grouped **property**, never a parameter: RFC 6350's quoted parameter value excludes `"`, so free text there has no in-band escape and `a";TYPE=work;X-EVIL="b` would inject parameters other address books honour. `N` gains its third component, and the dates emit `DEATHDATE` (RFC 6474) / `X-ODYSSEY-ESTABLISHED` / `X-ODYSSEY-DISSOLVED`. Import merges (never replaces), keeps a stored label over an incoming blank one, strips control characters rather than skipping the card, truncates an overlong label, and drops the overflow past 32 as a counted reason group. A contact with no aliases and no middle name exports **byte-identically** to before.
- **Wording.** The card's ⋯ item reads **New alias** and the dialog's button **Create alias** — the system's create/new convention, applied to an entity the user authors.

**Where it surfaces.** `components/ContactAliases.jsx` (the section, tiles, dialog and gates) · `ui_kits/web/Contacts.jsx` (seed, card chip, `New alias` add-kind, the four scalars in `AddContactModal`, the search arms) · `components/ContactSelect.jsx` (the lifecycle suffix). Specimens: `components/contact-aliases.html`, `preview/62-dialog-new-alias.html`, `preview/43-dialog-new-contact.html`.

> **Privacy, stated once.** An alias can be a maiden or former name and a date of death is data about a deceased person, so all five fields are personal data and two are special-category-*adjacent* — and an explicit "maiden name" label states outright what an unlabelled alias only implies. They are gated by the same `contacts.*` claims as the rest of the record, excluded from the finance embed a `transactions.read`-only caller sees, never written to a log line, and removed by cascade with their contact. The bulk vCard export now yields them too, which the export dialog says in one line.
