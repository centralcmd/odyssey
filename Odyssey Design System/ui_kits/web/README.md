# Odyssey · Web UI kit

Hi-fi recreation of the Odyssey web app (Blazor WebAssembly / MudBlazor v8). Open `index.html` to interact — login at the top, then navigate via the drawer.

## What's invented (because the repo doesn't have it yet)

- Dashboard, Accounts list, Transactions list, Budgets, Receipt review screens — there are no `.razor` files for these yet. These layouts are this design system's proposals.
- The Tax Statements and Insurance Policies pages — proposed surfaces for those backend features; their visual/interaction design is this system's contribution.
- The Subscriptions page — a proposed surface for the Subscriptions backend feature (recurring subscriptions kept purely on record); its visual/interaction design is this system's contribution.
- The Journal + Tasks pages — proposed surfaces for the Journal module spec (shared journal + shared kanban to-do list); their visual/interaction design is this system's contribution.
- The Calendar module's **ICS (.ics) import/export** — the frontend design for the ICS import/export feature (per-calendar export download + the import dialog with recurrence-rule mapping, reason-grouped skips, and the regenerate-future warning). The prototype's export builds a real `.ics`; the import simulates the parse (`calendar-data.js` `mockImport`) to exercise every result state.
- The **User Profile / display-name** feature (this pass) — the frontend for the spec: the Account → Profile card, the first-sign-in Onboarding gate, and the shared `profile-fields.jsx`. Attribution surfaces (Journal/Tasks/Photos/Albums authors) already render display names, matching the claim-aware resolver that replaces the old `UserName ?? Email` label; `/users` shows the resolver's resolved label (`DisplayName ?? FirstName`, with a display-name override on a few seed rows).
- The **License / Terms-of-Service acceptance** feature (this pass) — the frontend for the spec: the `/accept-terms` first-login / mid-session interstitial (two-step scroll-gated wizard, independent accept/decline, unavailable-document Continue fallback), the admin **Legal Documents** panel in System Settings (versioned ToS authoring + publish + retained history + on-demand viewer), and the registration License/ToS review (checkbox + read-in-Modal links). License compliance is tied to a SHA-256 of the repo `LICENSE`; ToS content is admin-versioned. Seeded from `legal-data.js`; the real app reads `GET /api/legal/*`.
- The **admin password-reset** feature (this pass) — the frontend for the spec: the `/users` **Send password reset** action (row menu item, warning-toned `lock_reset` confirmation modal, four honest outcome toasts, and the **Password reset pending** chip in the row's Account-status cell + detail panel), the nav-less **`/change-password-required`** forced-reset gate a target meets when signing in with the old password, and the shared **`PasswordChangeForm`** (DS component `components/PasswordChangeForm.jsx`) that both `/account`'s change-password section and the gate now render so the triad can't drift. Outcomes are driven by the Tweaks panel (*Users · Send password reset* and *Admin · Password reset gate*).
- The **Subscriptions summary limits** (runtime-configurable system settings, round 4 — this pass) — the frontend for the spec: a new **Subscriptions** group on `/settings` (icon `subscriptions`, placed after Contracts so the three finance-module groups sit together) carrying the three limits that govern the Subscriptions page-header roll-up — *Upcoming renewals window* (45 days, 1–365), *Max renewals shown in summary* (6, 1–1000) and *Max subscriptions read for summary* (1000, 1–100000, the one value that did not exist before: the summary's fetch was unbounded). All three take `system-settings.update` (`claim: 'count'`), so the group is fully editable for an ordinary settings admin and carries no mixed-permission band. No advisory on any of the three — lowering is what reduces work here, so an "above the shipped default" band would fire on the value closest to today's unbounded read — and no `lower only` / `raise only` marker, since all three move freely in both directions. Seeded values are stamped `meta: null` (never admin-owned, matching the migration's `UpdatedBy = null`). No new component and no page code: the three rows are declarations in `system-settings-data.js` rendered by the existing `SettingField` + `NumberField` machinery. The Subscriptions page itself is unchanged at the seeded defaults.
- The brand palette (Tide / Sea / Mint / Coral on Ink). Replace with whatever ships in `MudTheme`.## What's cut

- Real API calls. Everything reads from `data.js`.
- Validation, auth state, error boundaries.
- The MudBlazor table component is approximated with a CSS-styled `<table>` — close enough visually.

- The **mail transport settings** (runtime-configurable system settings — this pass) — the frontend for the spec moving `Email:SmtpHost`, `Email:SmtpPort`, `Email:UseStartTls` and `Email:ClientBaseUrl` out of deploy-time configuration into the settings store. Four rows open the existing **Email** group on `/settings`, above the sender identity and throttle they frame: **SMTP host** (text, `allowEmpty` — empty legally means *mail is not configured*; hostname-or-IP shape validation rejecting a scheme, port, path, userinfo, CR/LF/NUL, canonicalised to lowercase with a trailing dot stripped), **SMTP port** (number, 1–65535), **Use STARTTLS** (the group's first switch) and **Client base URL** (text, `allowEmpty`, absolute https except for loopback, no query/fragment/userinfo, a path allowed but normalised without its trailing slash). All four take `system-settings.security.update`. No new control type: existing `SettingField` + `TextInputField` / `NumberField` / `Switch` surfaces. Three page behaviours are new — a **row advisory** on the host and the STARTTLS switch stating, before Save is pressed, that the stored SMTP credential will be cleared; a **browser-side origin-mismatch hint** on the client base URL (the server cannot see the caller's origin, and an advisory composed there would re-fire on every load); and the **`SecretClearOnSaveDialog`** gate in front of the page's single batch Save, which submits the whole batch on Confirm, discards nothing on Cancel, and restores focus to the control that opened it. With the host empty the page contributes one `information`-severity entry to the page-header signal rollup ("Transactional mail is not configured", *In Email.*, Fix →) alongside the existing undecryptable-credential entries — gated, like the rollup itself, on the claim that can fix it. A save that clears the credential flips `secretEmailUsername` / `secretEmailPassword` to *not set* in the same commit and raises a warning toast naming where to re-enter them.
