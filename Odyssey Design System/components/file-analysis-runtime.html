File analysis — the switch, the model and the destination as settings

Three values leave appsettings.json for the settings store: whether documents may be sent at all, which model reads them, and where they are sent. All three take the security write claim, all three are audited, and each one carries the sentence a reader needs at the moment of the edit — the switch says what turning it on lets happen, the destination says that the configured API key goes with it.

1 · The three rows, at the top of the File analysis section

The switch and the destination frame everything below them, so they sit above the processor-disclosure rows rather than after them. Advisories are non-blocking, computed after the write commits, and never set aria-invalid. Only the host of the base URL is ever echoed — a gateway URL such as https://key:secret@gateway.internal/v1 is the expected shape here, so the host is parsed once at the advisory boundary and the rest is unreachable from the text.

2 · The base URL's shape — blocking, and as strict as the request builder

The provider resolves a root-absolute /v1/messages against this value, so any path would be silently discarded. Accepting one would mean the value that is saved and the value that is used differ, with nothing in the audit trail able to show it — so a path is refused rather than dropped. Private, loopback and link-local hosts are allowed: an internal gateway is the main reason this setting is editable at all.

3 · With analysis off, the affordance says so — before any document is picked

The switch is read live, so the file row's action menu reflects it. Analyze renders disabled with a one-line reason wired as its aria-describedby; the item keeps aria-disabled rather than the disabled attribute so it stays in the roving-focus order and a keyboard or screen-reader user reaches the reason instead of a silently skipped item. The consent gate is unreachable, so no consent is ever collected for a transfer that cannot happen. Meaning is carried as text, never by the dimmed state alone.

  • AI document analysis is turned off for this instance.

4 · The transfer record — the conditions a job actually ran under

Once the destination, the processor and the region are all editable, they are part of the conditions a transfer ran under, so all three are stamped on the job from one snapshot and never rewritten (GDPR Art. 30(1)(e); the region decides whether a transfer fell under Art. 44–49). The host only — never the path, query or userinfo. A job recorded before these columns existed reads Not recorded; back-filling it with today's setting would put a value into an audit record that was never observed.
