The token, not a probe, drives every state. ProfileDto.ProfileImageVersion (the caller's own) and ExistingUser.ProfileImageVersion (per admin row) are response-only Guid?s. Non-null means renderable by this caller — not merely "a row exists": the projection returns null wherever the read path would refuse, so an administratively disabled subject renders the monogram with no request at all. An <img> plus an error handler cannot drive a button label, and probing would mean a mostly-404 request per row.

Alt text follows what the image is. On /account it is the subject of its own controls — a descriptive alt. In a list row it is decorative (alt=""), because the adjacent cell names the person. In the detail panel the neighbour is a mono user id, so the mark carries the subject's resolved display name.

A load failure is silent, and per row. The fallback state belongs to the consumer — Avatar.onError only invokes the callback. On a 50-row table that means one flag per row, reset when the row's token changes; one page-level flag would blank every avatar after a single failure. No broken-image glyph, no toast.

There is no administrator write path. An admin can neither upload nor remove someone else's picture — the write endpoints take no user id at all, so there is nothing to tamper with. The remedies for an abusive upload are disable (which also stops the read) or delete (which cascades the bytes away), never editing another person's identity.
