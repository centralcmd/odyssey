Why a tile and not a chip. An alias needs a ⋯ menu at a ≥24×24 px target and a two-line body (value + label). Chip is a ~23 px nowrap pill with no positioning context and no class/style splat, so it cannot host one. The existing contact-method tile grid does not fit either: its model is positional, carries Primary, an enum label and an assigned column, and its entry count covers only addresses, emails and phones. Hence a sibling grid with the same tile shell.

The label is free text, on purpose. A user writes “maiden name”, “stage name”, “pre-merger name” or anything else without a schema change. The consequence is stated rather than hidden: the label is not filterable, not validated against a vocabulary and not localised, and two people may spell one concept differently. Alias values are searched (so “Kari” finds “Karoline”); the label is not, which is why the page's search placeholder reads Search name, alias or notes….

Rejections. Duplicate (409), cap (422) and validation (400) render inline on the value field with aria-invalid, move focus there, and raise no toast — a user must never get a snackbar and a field error for the same failure. Only a 404 (or a transport failure) closes the dialog, toasts, and announces. Deleting is immediate: no confirm dialog, matching the sibling tiles, since an alias is cheap to re-add.
