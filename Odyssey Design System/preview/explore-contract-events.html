Contract events · contracts/{id} → Events

A contract records what an agreement is. An event records what has happened to it — signed in August, rent renegotiated in February, notice served in June, and the two emails in between. The backend half is specified; this is a proposal for the front. It sits as a collapsible section under Parties and Documents, the same level as Terms, and renders as a vertical rail, newest first, with an optional horizontal spine above it for skimming a long life at a glance. The section is a read surface: creating an event is an action on the contract’s ⋯ menu, and search, filtering and sorting are not in v1. Events are written by hand and only by hand: pausing, archiving or renewing a contract writes nothing here.

  • edit_noteNothing is auto-generated, so nothing is locked. The spec is explicit that no event is system-written (§7.6, Non-Goal 4), and the surface follows: no “system” badge, no read-only rows, no two-tier list. Every entry is the user’s own and every entry is editable. The empty state says as much, so the first impression is “a log you keep”, not “a log that fills itself”.
  • playlist_addThe section carries no create button. “New event” sits in the contract’s ⋯ menu with the other things you do to a contract, so the log reads as a record rather than a form. The empty state says where to find it rather than growing a button of its own.
  • vertical_align_centerBoth ends of the rail are anchored to a real date. Newest-first means the top is the present, so page one opens on Today — the log is live, and the next entry lands there. The foot is when the contract record was added — deliberately not its start date, since a contract can start in 2026 and still carry a “signed” event from 2025, which would put an event below its own origin. It is placed chronologically rather than pinned, because an event can legitimately be backdated before the record existed; usually it is older than everything and lands at the foot anyway. Mid-pages get neither cap and the line fades instead: it genuinely does continue, and a hard stop there would say otherwise.
  • timelineThe rail is the log; the spine is the overview. A horizontal axis has nowhere to put a title or a description, so the spine carries only position and type colour — the whole life of the contract in one strip — and clicking a node highlights that entry in the rail below. On a two-event contract it does not render at all.
  • inventory_2An archived contract is still writable here (§8.6) — unlike Terms, which goes read-only. Archival hides a contract from the default list; it does not lock its history. This is a deliberate divergence from the section directly above it, so it is drawn rather than assumed.
  • segmentThree free-text fields, three jobs. The title labels the entry, the description is the account of what happened and sits under it on the rail, and notes are the user's own working notes, which the rail never shows. That last one is a presentation rule only — notes sit behind the same claim, are searched by the same term and are exported with the rest.
  • groupsThe notes field says who can read it. contracts.read is held by Admin, Owner and User, so in a household install “not on the timeline” still means everyone but Guest can read it. The helper text says so outright, and the label is never “Private note” — a user who mistakes the field for private storage will put things in it the label promised to protect (§4.1).
  • link_offNo links, so nothing to guard. v5 removed the four contact and account columns (Non-Goal 5), and with them the RESTRICT keys, the 409 blocker payloads and both detach valves. DELETE /api/contacts/{id} and DELETE /api/accounts/{id} are untouched by this feature, so the composite-refusal dialog earlier drafts needed is gone from this page too. There is no 409 anywhere in the feature.
  • toggle_offA Terminated event does not expire the contract (§4.2). Status is derived from the contract's own dates and archive flag, never from the log — so nothing in this section touches the status chip, and the rail must not imply that logging a termination changes what the contract is.

Open questions for you

  1. Auto-generation. You mentioned events being written when a user pauses a contract; the spec forbids it. This proposal keeps the spec. If the intent stands, the cheapest version is a pre-filled dialog on Pause / Renew / Archive that the user confirms — still user-authored, no backend change, no locked rows. The expensive version is a system/user distinction in the entity, which changes §4, §7.6 and the edit rules.
  2. Does the collapsed contract row show anything? An event count beside Parties / Documents, or the most recent entry, is listed as “later, not committed”. A count is one extra column on the list query; the latest entry is not.
  3. A generated sentence was tried and dropped. The rail briefly read “Email was sent from Anna Sørensen to Michael Chen at 3 Apr 2026 09:15”, composed from the type, the moment and the links that existed at the time. It duplicated the user’s own wording sitting beside it, and §4.1 makes Title required and authoritative — so the rail is title · date. v5 then removed the links the sentence leaned on, so reviving it would now compose from the type and the date alone.
  4. Where does search land when it arrives? The endpoint already carries Search, Types and SortBy. Deferred out of v1, the 220-entry stage below is what a user gets without them — reachable, but only by paging. Worth a fast follow, or genuinely fine?
  5. Should the spine be the default, or the option? It reads well on a five-year lease and poorly on a three-month service contract. Currently the option. It also has a density limit: past forty entries a node per event is an overlapping band, so the 220-entry stage below switches to one bar per month, coloured by that month’s dominant type. Is the binned version worth keeping, or should the spine simply disappear on a log that long?
  6. Does the description earn a second line on every row? The rail now shows title then description, clamped to two lines. On the lease that reads well; on a log of twelve one-liners it is mostly whitespace. The alternatives are description on hover, or description only in the dialog alongside notes.
  7. Is “Notes” the right label, given who can read it? The spec forbids anything implying privacy and the helper text states the audience, but the word still invites the assumption. “Working notes”, “Reminders” or “Follow-up” each carry less of it.
